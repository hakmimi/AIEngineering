# Limitations, weak points and the next four weeks

Written on Day 56 after re-reading the evidence. Everything here is a known weakness, not a hypothetical one.

## 1. Where the model still fails (LLM review notes)
| Observation | Evidence | Consequence |
|---|---|---|
| LLM explanations score below the template (9.5 vs 10 on our rubric) | `docs/FINAL_EVALUATION.md` | the model adds readability, not measured quality |
| The lowest-scoring explanations (8/10) use internal jargon: "the rules engine identified the reason code NEW_CUSTOMER_HIGH_AMOUNT" | `data/eval/report_v4.md`, section "Lowest-scoring AI explanations" | customer-facing wording needs a prompt rewrite or template-only for customers |
| The LLM changed 0 of the 45 evaluated decisions | Day 40 evaluation | its decision-review role is untested on cases where it *should* disagree |
| In `ai` mode (no policy gate) one run over-blocked a valid case (`n11_only_option_bank_br`) that another run did not | `scripts/compare_modes.py` runs | temperature 0 is not deterministic; single runs can differ by a case |
| ~1.9 s per reviewed decision; p95 2.5 s | Week 3 simulation | fine for review queues, too slow for an inline authorization path |

## 2. Where the data is weak
- Everything is synthetic and generated by our own code; hidden "truth" columns exist only because we made the world.
- 45 evaluation cases, written by the same person who wrote the rules; the 8 hold-out cases are not independent.
- No real chargeback outcomes, so "correct" means "agrees with our expected decision", not "prevented fraud".
- Traffic mix is invented; the fast-path share (25-32%) and the cost per decision depend on it.

## 3. Where the system is weak
- **Docker image never built**; CI workflow never run on GitHub (both listed in earlier READMEs).
- Single process: in-memory job queue and SQLite; no multi-instance safety, no Postgres, no external queue.
- Rate limiter and API key are basic (one shared key, in-memory counters).
- No authentication per client, no PII handling review, no data retention policy for the audit table.
- Policies and thresholds are code/config-driven and reviewed only by tests, not by a business owner.

## 4. Data improvement backlog (what would make the data more realistic)
1. Real or partner-provided labelled transactions (even 500) with outcomes: approved / chargeback / fraud.
2. An independent reviewer writes new evaluation cases without seeing the rules (a true hold-out).
3. Seasonality and bursts in the traffic generator; correlated fraud rings (same device/card across accounts).
4. Provider outages and slowdowns as scenarios, to test fallback routing.
5. Multi-currency amounts with realistic FX and fee schedules.

## 5. Next four weeks
| Week | Focus | Deliverable | Done when |
|---|---|---|---|
| 1 | Verify what is only claimed | build and run the Docker image; run CI on GitHub; fix what breaks | `docker compose up` passes `/ready` on a clean machine; CI green |
| 2 | Better evidence | independent hold-out set, repeated runs (n=5) per mode, confidence intervals; error analysis by category | the report gives ranges, not single numbers |
| 3 | Shadow mode + human feedback | log decisions next to a "human" label field; measure agreement; feedback loop into the eval set | agreement rate and disagreement review process exist |
| 4 | Scale and hardening | Postgres audit store, external queue (or Redis), per-client keys, retention policy, load test at 10x | tested failover; no single point of state |

Stretch topics from the reading list: retrieval of similar past decisions as a *tool* (Project A skills applied to Project B), and a cheaper model for the explanation step with the same grounding checks.

## 6. What I would not do
- Give the LLM decision authority because it "looks smart": nothing in the evidence supports it.
- Claim accuracy numbers without saying they come from a self-written set.
- Add features before the two verification items in week 1.
