# Day 30 – Synthetic Business Data

## Goal

Build the data layer the decision agent will run on: a provider reference table, risk reference tables and **1,000 realistic synthetic transactions** with hidden ground truth (risk, fraud, approval outcome) – plus a loader the agent uses so it never touches files directly.

```text
Synthetic Data → Data Files (CSV/JSON) → Data Loader → Decision Agent Context
```

## How it was implemented

1. **Transaction fields** – the Day 29 model plus four *hidden* columns: `simulated_risk_score`, `is_fraud`, `historical_provider`, `approved_outcome`. The agent must never see these; `iter_transactions()` drops them, a test proves it.
2. **Provider table (6 providers, deliberately different)** – global card processor (2.9 % + 0.30), bank-transfer specialist (0.8 %, slow, 100k limit), regional wallet, expensive high-risk-tolerant fallback (4.2 %, accepts risk up to 0.8), Israel-local (1.9 %, 200 ms), budget card processor (1.6 % but 96 % uptime, 3k limit, low risk tolerance). Each has countries, currencies, methods, fee %, fixed fee, base approval rate, max amount, uptime, `max_risk`, latency – the constraints Day 31's eligibility rules will use.
3. **Risk model of the world** – `logit = −3 + 3.2·country_risk + 2.4·category_risk + 0.9·new − 0.6·vip + 0.35·max(log(amount/median),0) + 0.7·chargebacks + noise`, passed through a sigmoid. Country risk 0.07 (DE/NL) … 0.55 (NG); category risk 0.05 (groceries/utilities) … 0.35 (digital goods/gaming).
4. **Distributions** – 15 countries weighted by traffic; 7 merchant categories; 25 % new / 65 % returning / 10 % VIP with consistent account ages; card 70 % / wallet 20 % / bank transfer 10 %; amounts log-normal around a per-category median (groceries ≈ 60 … luxury ≈ 1,500 USD, scaled per currency, heavy right tail); home currency 80 % of the time; timestamps uniform over 30 days.
5. **Outcomes** – fraud is rare (`0.35·risk²` ⇒ ≈ 1 %); the historical provider is chosen at random among providers that *could* carry the payment; `approved_outcome = Bernoulli(base_rate·(1 − 0.4·risk)) and not fraud`.
6. **Which format?** CSV for the 1,000-row table (loads straight into pandas), JSON for small nested reference data (lists of countries/methods). Loaders hide that choice.
7. **How does the agent access data?** Only through `data_loader` (cached, validated, typed errors), so orchestration code is storage-agnostic.

## Assumptions to criticise (documented, not hidden)

- The world is *generated by the same kind of model the agent will use* (risk grows with country/category/newness/amount/chargebacks) – the agent will look competent partly for that reason; real data would be messier.
- Country and category risk numbers are plausible guesses, not statistics; fraud rate (1.2 %) and approval rate (83 %) were tuned to look like real payments – an earlier draft produced 10 % fraud and 74 % approval and was corrected.
- No seasonality, no repeat-customer velocity, no card BIN/device signals.
